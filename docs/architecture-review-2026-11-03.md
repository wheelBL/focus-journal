# 架构检查与本轮调整

检查对象：专注记 0.37.0，TypeScript / React / Electron / SQLite。检查基于源码、依赖关系和合成测试数据，没有读取个人日志或服务密钥。

## 判断

基本分层合理，适合当前个人桌面应用，暂不引入 DSH 或插件平台。React、AI 与本机 API 共享 JournalService，业务规则与原子保存只有一个最终入口；Electron 控制器负责系统资源和 IPC，渲染器不直接访问数据库。保留这个结构，比把所有模块插件化更有价值。

职责尚未完全清晰。本轮发现的真实问题集中在操作入口、历史管理、组件依赖和命令结果，而不是技术栈选择。

## 已修复

| 问题 | 原因与风险 | 调整 |
| --- | --- | --- |
| 快捷键只能撤销部分操作 | App、任务树和原生菜单各自分派，整理历史与状态历史分离；Shift+Z 也可能落入撤销 | `useEditActions` 统一编辑动作路由，`core/history` 管理同一有界撤销/重做序列；输入框保留原生文字操作 |
| AI 无法接着讨论 | 每次请求只发送本轮问题；应用结果未成为后续对话事实 | `ai-conversation` 负责有界会话与上下文构造，`AiAssistantService` 负责生成与应用，Electron 的 store 负责本机持久化 |
| AI 把审视变成普通任务 | 可用业务命令与上下文缺少事项审视安排 | AI/API 使用原有 `item-review.configure` / `defer`，展示真实安排；保留已有周期，默认单次；不自动标记已审视 |
| 两处组件运行时循环依赖 | 重复安排组件引用提醒页面里的转换弹窗；详情主体与关联详情容器互相依赖 | 独立 `ReminderConvertDialog`，拆出不依赖关联导航宿主的 `ItemInspectorBase` |
| 新建后可能选错内容 | 笔记和提醒通过新旧快照差集猜测创建 ID，可能混入 API/AI 的并发新增 | 命令响应带 `commandResult.createdItemIds`，由同一次提交计算；普通快照与持久数据不包含此临时结果 |

撤销只恢复受影响业务字段，先校验当前值和依赖；投入、计时片段和活动历史不回退。已发生真实投入的新建事项不能通过撤销抹除。撤销栈限当前应用运行期间；重启或替换日志后清空。审视“已审视”记录仍使用该流程已有的专用撤销；计时、补记投入和同步不假装是可任意重放的普通编辑。

## 保留的职责分工

| 部分 | 负责 | 不负责 |
| --- | --- | --- |
| `JournalService` | 领域校验、一次命令的原子提交、保存后发布结果 | UI 焦点、对话展示、原生窗口 |
| `core/history` | 字段级撤销/重做、冲突与依赖检查 | 整个数据库回滚、计时重放 |
| `core/control-api` | 外部命令 schema、允许的输入与映射 | 绕过领域校验、直接 SQL |
| `core/ai-assistant` | 授权范围的上下文、建议约束与预览 | 写文件、操作窗口 |
| `AiAssistantService` | 当前生成/取消/应用生命周期、会话协调 | 服务密钥存储、渲染界面 |
| `ai-conversation` / Electron store | 有界历史表达 / 设备本机原子持久化 | 业务数据同步、持久化可直接执行的旧计划 |
| `useEditActions` | 原生菜单与应用快捷键的统一动作路由 | 重新实现浏览器文本编辑 |
| React 页面与详情组件 | 选择、草稿、焦点、编辑与展示 | 猜测提交结果、另建业务规则 |
| Electron 控制器 | 窗口、托盘、生命周期和受限 IPC | 复制第二套计时或事项状态 |

## 后续值得优化，但本轮不扩大的部分

1. `JournalService` 仍承载较多命令族。可按提醒、事项、审视拆出领域处理器，但保留唯一提交边界，避免每个模块自行保存。
2. 命令定义分布在 API schema、AI 允许列表、撤销策略和操作记录名称中。它们的权限范围本来就应不同；适合建立显式元数据与覆盖检查，避免新命令漏配，不应直接把服务全部命令开放给 AI。
3. `Projects` 同时协调过滤、位置、创建草稿、选择和拖拽。下一步应优先抽出创建与拖拽的交互控制，保留现有选择和草稿契约；仅把 JSX 切成小文件不能解决职责问题。

静态依赖检查不包含动态导入和仅类型导入；消除循环依赖不等于证明所有运行时路径无问题，仍需组件交互和隔离桌面验证。真实服务的模型质量也不能由模拟 AI 测试推断。
